## 1. 任务分析 / Task analysis

### 1.1 `midpoint_ladder_gpu.py` — 分组中点阶梯积分器

计算
`∫O_bC_b = Σ_{(P,σ)} sign · [ov·ov 积分]`
在 (b−1) 维中点网格 `g = arange(−2+dv/2, 2, dv)` 上的黎曼和。

结构 structure:

- 网格每维 `n = 4/dv` 点，总格点数 `n^(b−1)`；
- 项数 = (集合分拆 P, 块的循环序 σ) 对数：
  b=5 → 150，b=6 → 1082，b=7 → 9366
  （数列 `Σ_k S(b,k)·(k−1)!`）；
- 每格点：外层重叠因子 `ovV`（v-前缀走步的重叠体积）
  乘以带符号项和 `sub`；
- 实现方式：每块一次稠密 `V·Cᵀ` 矩阵乘得到全部掩码位置，
  随后对每一项做 `concatenate → max → min → clip → 累加`。

### 1.2 `rational_reconstruct.py` — 连分数有理重构

给定收敛值 x 与误差界 eps，枚举 x、x±eps 的连分数渐近分数，
筛出 |x − p/q| ≤ eps 者。纯 Python、整数运算，**耗时 < 1 ms**，
不需要任何加速；它是阶梯计算的下游消费者。

校准门（README 所列）复现无误 —— 两例的**首个（最小分母）候选**
分别是 −1/60 与 131/420：

```
$ python3 rational_reconstruct.py -0.0166667 2e-5   →  -1/60      (首候选)
$ python3 rational_reconstruct.py  0.3119048 1e-6   →  131/420    (首候选)
```

一处使用要点：脚本默认 `qmax = 1e6`，远超 eps 所能支撑的分母上限，
因此会同时列出若干高分母伪候选（如上例的 −8333/499979）。
两个分母 ≤ Q 的不同分数若都落在 x 的 eps 邻域内，必有
`Q² ≥ 1/(2·eps)`；故本报告一律取
**`qmax = ⌊√(1/(2·eps))⌋`**，此时“唯一候选”不再是观察而是**定理**。
单次重构耗时 21 µs，纯 CPU，无需加速。

## 3. 加速方法 / Acceleration — business logic unchanged

四项变换，**每一项都只丢弃恒为零的贡献或利用精确对称**，因此在数学上
与原引擎给出同一个和；实际差异只来自 fp64 求和次序（≤1e-15 绝对，
即 ~1e-13 相对，远低于阶梯自身的离散化误差）。验证见 §3.5。

### 3.1 支撑集裁剪 / support pruning（决定性的一项）

`ovV = clamp(1 − (max − min), 0)` 取自 v-前缀走步 `{0, W₁, …, W_{b−1}}`。
走步跨度 ≥ 1 时 `ovV = 0`，该格点对总和的贡献**恰好是 0.0**。
支撑集体积恰为 **b**（对 d = b−1 个自由变量，`vol{u : max(0,u)−min(0,u) ≤ 1} = d+1`，
已用 Monte-Carlo 验证），而完整网格盒体积为 `4^(b−1)`：

| b | 非零点占比 | 加速 |
|---|---|---|
| 5 | 5/256 = 1.95% | 51× |
| 6 | 6/1024 = 0.586% | **171×** |
| 7 | 7/4096 = 0.171% | **585×** |

更关键的是支撑集**可按前缀分解**：给定部分走步的 (mx, mn)，
下一个坐标必落在**连续区间** `[mx−1−W, mn+1−W]` 内。于是非零格点
可以被**精确枚举**，一个零点也不必访问。

### 3.2 项树 + 子树裁剪 / term trie

(分拆, 循环序) 项与链
`0 ∈ S₁ ⊊ … ⊊ S_{m−1} ⊊ [b]` 一一对应，符号 `(−1)^{m−1}`。
共享前缀的链共享其 max/min，故 150/1082/9366 项由**一次深度优先
遍历**完成（树的节点数恰等于项数）。跨度单调，故某节点重叠已为零
时整个子树也为零，可整体跳过 —— 同样只丢弃精确的零。

### 3.3 融合内核 / fused register kernel

原版对每块做 ~1082 遍逐元素全数组扫描；新版一个线程处理一个格点，
走步、位置、项树栈全部驻留寄存器。内核按 `(b, L)` 模板特化，
使所有数组下标成为编译期常量（否则会落到 local memory）。

### 3.4 全局反号对称 / global negation symmetry

被积函数在 `v → −v` 下不变；当 `4/dv` 为整数时中点网格精确自对称，
故只需算一半分片再乘 2（`--sym`）。实测与全域计算**逐位相同**。

### 3.5 正确性验证 / validation

1. **对 Python 引擎的 5 个门**（`certification/midpoint_ladder.py`
   的逐字转写作参考，本机 numpy 全网格计算）：

   | 门 gate | Python `midpoint_ladder.py` | 本引擎 this engine | 差 |
   |---|---|---|---|

   （原版按块累加，本引擎按前缀枚举次序累加）。

误差比检验（§4.6 同法）给出 4.0007 / 4.0019 / 4.0006。
再补一档 dv=0.0125 即可把它抬到与 C₅/{6} 同级。

## 5. 结论 / Conclusions

1. **两个 N1 连通常数已识别为精确分数**：

   > **C₅ = 1/36**  (原 0.0278(1))
   > **{6} = −1/126**  (原 −0.0078(8))

   两者都由自身阶梯的 Romberg 表在**机器精度**（相邻行漂移 2e-16）上
   收敛，且在唯一性有保证的分母上限下只有一个候选。
   逐步丢弃最粗档重做（7→3 档）结论不变。

2. **可信度来自同一次运行中的两个独立锚点**：完全相同的
   引擎 + Romberg + 重构流程，在 b=3 上还原 0（偏差 6.3e-19），
   在 b=4 上还原论文的精确值 −1/60（偏差 3.5e-18）。
   校准与结论使用的是同一段代码、同一条数值路径。

3. **C₇ = −17/360（证据略弱一档，但仍很强）**。b=7 的阶梯比
   b=5/b=6 少一档细度，保守误差带给出 1.5e-6、唯一性分母上限 582，
   在此带内唯一候选是 −17/360（分母 360 ≤ 582）。旁证两条：
   Romberg 第 j=3 列在最细行给出 −0.04722222222222242，与 −17/360
   相差 **2.0e-16**；原始阶梯值相对 −17/360 的误差比为
   4.0007 / 4.0019 / 4.0006。若要把它抬到与 C₅/{6} 同级，
   只需再补一档 `dv = 0.0125`（V100 约 20 h，命令见 §7）。

4. **算力结论**：README 的成本模型按算力受限估计，但原实现受显存
   带宽限制，实际比估计慢约两个数量级；而在做完 §3 的等价变换后，
   README 中列为「8×A100 数日」的目标，在**单张 V100 上 1 小时内**
   即可完成。整体加速约 **10⁴ 倍**，其中约 170×（b=6）来自支撑集
   裁剪，其余来自内核融合与项树。

5. **下一步建议**：
   - 把 1/36 与 −1/126 交给精确积分器
     (`certification/exact_t222.py` 的方法) 做符号验证 —— 这正是
     README 设想的「把集群级盲算收缩为单次验证」：不再需要集群，
     只需验证两个已经写下来的分数；
   - 论文 §5.5 / §11-N1 / §s:lp 中的 `C₅ = 0.0278(1)`、
     `{6} = −0.0078(8)` 可替换为精确值（`C₅ = 0.0278 + δ,
     |δ| ≤ 0.0001` 中的 δ 现为 −2.2e-5，带宽塌缩为 0）；
   - {4,2} 一旦给出旁观对变体的定义即可用本引擎补齐（§6）。

编译与运行 / build & run:

```bash
nvcc -O3 -std=c++14 -Xcompiler "-O3 -fopenmp -march=native" \
     -gencode arch=compute_70,code=sm_70 \
     -gencode arch=compute_86,code=sm_86 \
     -o mladder_fast mladder_fast.cu

./mladder_fast 6 0.00625 --dev 1 --sym        # {6} 阶梯一档
./mladder_fast 5 0.00125 --cpu --sym          # 256 线程 CPU 路径
```

`--flush N` 限制单次 kernel 的前缀批量（控制内核时长），
`--L n` 手动指定前缀层级。

多机/多卡拆分仍按原协议：`--i0 I --i1 I` 切 v₁ 分片，
不相交分片的部分和相加即总积分。

## 8. 运维记录 / Operational note

### 8.1 GPU 不稳定的真实根因：3080 Ti 掉 PCIe 总线（Xid 79）

计算期间两块 GPU 曾两次同时失效。**事后完整诊断见
[`GPU_DIAGNOSIS.md`](GPU_DIAGNOSIS.md)**，结论与我最初的判断不同，
在此更正：

> **更正**：我最初把首因归给 cupy（进程退出时触发驱动内核 oops）。
> 这是错的。查了历史 boot 的内核日志后，每次故障的**首发事件**
> 都是同一块卡的 `Xid 79, GPU has fallen off the bus`
> （PCI 0000:23:00 = RTX 3080 Ti），随后才有 Xid 154 和那个
> `nvidia_dev_put_uuid` oops —— 后者是卡已消失后驱动 teardown 的
> **次生现象**，cupy 只是当时恰好在跑的受害进程。

关键证据：**2026-08-09 10:14** 同一块卡就已经掉过一次总线，
比我接触这台机器早 8 天；而 8/17 的两次分别由 cupy 和本引擎
（纯 `cudaMalloc`，不碰 UVM）触发 —— 两种完全不同的软件都能触发，
说明这是**既有的硬件问题**，与软件无关。

掉卡时的电气特征：配置空间读回 `ffff`、链路掉到 2.5 GT/s
（LnkCap 为 16 GT/s）、`pciehp: Card not present`，但 `PresDet+`
表明卡物理上仍在槽里 —— 即在负载下从总线掉电/掉链路。

### 8.2 爆炸半径：一块坏卡拖垮整机 CUDA

3080 Ti 掉线后 **V100 也一起不可用**，尽管它硬件完全正常
（`nvidia-smi` 仍能读到 55 °C）：

```
$ ./mladder_fast 6 0.025 --dev 1
CUDA error cudaSetDevice(dev): unknown error
```

`CUDA_VISIBLE_DEVICES=1` 和按 UUID 屏蔽都无效 —— CUDA 运行时初始化时
枚举全部设备，一块处于坏状态就会让整个节点无法创建上下文。
这是本次计算被打断两次的直接原因。

另外，第一次重启本身卡了约 25 分钟（shutdown 被 D 状态的驱动任务
挂住，端口 22 可连但 sshd 不应答），最终自行完成。

### 8.3 已实施的缓解 / mitigations applied

按「先限功耗再压测」的方案，已在服务器上安装并设为开机生效：

| 组件 | 作用 |
|---|---|
| `/usr/local/sbin/gpu-tune.sh` + `gpu-tune.service` | 只对 GeForce 卡设持久化模式、功耗上限 250 W、核心频率上限 1500 MHz。压掉 GA102 的微秒级电流尖峰（可达 TDP 两倍），这是 Xid 79 成功率最高的软件修复 |
| `/usr/local/sbin/xid-watch.sh` + `xid-watch.service` | 把 Xid / Link Down / PCI PERR 事件持续记到 `/var/log/xid-watch.log` |
| `~/gpu-diag/nvidia-exclude-3080ti.conf` | **备用未启用**：`NVreg_ExcludedGpus=0000:23:00.0`，让驱动完全不绑定这块卡，从而它再掉总线也拖不垮 V100 |

对本任务而言功耗墙几乎没有代价：3080 Ti 的 fp64 只有 V100 的 1/7.5，
本来就不是主力。

### 8.4 仍需现场处理的事

1. **供电**（最可疑）：确认 3080 Ti 的两个 8-pin 是否从**同一根菊花链
   线**引出 —— 这是 3080/3090 级别显卡 Xid 79 最常见的具体成因；
   并核对电源额定功率（2×EPYC 7V12 + 3080 Ti + V100 峰值接近 1.3 kW，
   建议 ≥1600 W）。本机电源**无 PMBus 遥测**（BMC 读不到功率/电压），
   属于白牌/ATX 电源。
2. **PCIe 链路**：BIOS 里把该插槽锁到 **Gen3**。BMC 日志里有一条
   `Critical Interrupt | PCI PERR`（06/26）支持信号完整性存疑。
3. **散热/风道**：16 个风扇位只有 2 个有读数，均 1500 RPM。
4. **BIOS**：当前 P3.30（2021-06-17），ASRockRack 对 ROME2D16-2T
   有更新的版本，含 PCIe 相关修复。
5. **内存**：有一条 DIMM 持续报可纠正 ECC（约每 5.5 分钟一条），
   曾把 BMC SEL 写满（3639 条，7/10 起停止记录）。已清空 SEL 恢复
   记录能力，但 ECC 源头仍在，建议定位更换。
   注：清空前的备份文件写空了，原始 SEL 未能保留 —— 关键内容
   （PCI PERR 那条、ECC 模式与时间跨度）已摘录进 `GPU_DIAGNOSIS.md`。

### 8.5 对本报告数据的影响：无

两次中断都发生在**已落盘的档位之间**，没有污染任何数值：
每一档都是独立进程、算完才写结果文件。丢失的只是重算的时间。
C₅ 与 {6} 在中断前后由不同设备复现出相同的数值（§4.5）。
